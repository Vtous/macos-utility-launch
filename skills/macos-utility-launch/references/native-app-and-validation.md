# 原生实现与真实验收

## 实现选择

原生菜单栏工具可考虑 AppKit 管理菜单栏与窗口生命周期，SwiftUI 构建设置界面；遵循现有项目架构，不因该案例强制换框架。选择目标系统支持的公开 API，按实际需求决定依赖、沙盒和权限。

将可独立判断的规则与系统集成分开，使暂停、优先级、默认值、配置校验等能够可靠检查。不要把 OtterMate 的输入法 API、重试时序或特定系统版本推广到其他产品。

对自动化动作写清“什么时候做一次、何时取消、用户手动修改后怎样处理”。必要时采用有限重试；避免通过持续强制修正掩盖时序问题。并非所有产品都需要重试或允许手动覆盖，依据需求决定。

## 数据与生命周期

需要持久配置时考虑原子保存、读取失败保护、导入前校验和备份。配置损坏时避免静默覆盖用户原文件。文件权限不等于加密；导出的应用路径等内容也可能泄露个人信息。

菜单栏应用需验证首次启动、关闭设置后常驻、重新打开设置、退出、重复启动以及可选登录启动。登录启动使用项目适用的系统机制，核对其状态；未经要求不要为测试改变用户的自启设置。

## 验证层次

| 验证 | 可以说明什么 | 不能代替什么 |
|---|---|---|
| 源码与静态检查 | 所检查代码的功能与权限调用 | 独立安全审计、所有依赖运行行为 |
| 核心自动检查 | 实际覆盖的规则和持久化行为 | 系统前台切换、权限界面、所有 UI |
| 真实交互 | 当前机器与场景下的实际行为 | 全部机型、系统版本与第三方应用 |
| 签名/ZIP 检查 | 所验证包的签名及内容完整性 | 苹果公证、恶意软件扫描结果 |
| 公证票据验证 | 指定应用附带票据的验证结果 | 所有机器当前 Gatekeeper 接受结果 |

选择与变更匹配的测试。局部图标修改无需重做不相关业务测试；涉及构建、签名、升级和行为时保留必要检查。测试数量不是质量指标。

## 交互测试的准备

先创建隔离配置和必要的空白测试对象，明确哪些状态隔离不了。对 OtterMate 类工具，即使配置独立，实际运行仍可能切换系统输入源。

给配合测试的用户短步骤和可观察结果，例如：“点 B，等两秒检查 ABC；点 A，检查中文输入法”。工具受限时，只请用户完成无法代做的必要动作；不要连续让用户找窗口、猜状态。记录界面、日志与用户反馈之间是否一致，不采集无关输入内容。

菜单栏没有普通窗口时，可设计正常的“打开设置”入口；如提供命令行参数，应为产品可解释的用途。不得为了测试擅自授予全局控制权限。

## 验证记录

记录版本、构建、架构、系统、测试动作、结果与限制。区分“App 退出重开”“电脑重启后登录启动”“登录项开关存在”；三者不能互相代替。公开说明去掉个人路径和使用记录。

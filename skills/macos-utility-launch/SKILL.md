# macOS 小工具开发与发布

将原生 Mac 小工具推进到用户当前需要的可用状态。工作依据是项目源码、实际运行行为和交付物，保留用户已经确认的功能与品牌选择。

## 从原型推进到交付

1. **确定一个可验收的动作。** 写清触发条件、预期结果、暂停/失败行为和不应破坏的现有行为。先验证系统 API 能否解决问题，按实际需要选择权限与依赖。
2. **先跑通功能原型。** 分离纯规则与系统集成；为会影响结果的核心决策做合适的检查，为系统交互安排真实使用测试。不要用编译成功代替功能实测。
3. **正式打包前确认品牌。** 临时名称可用于原型；确定中英文名称、应用名、菜单名称和发布名称后再统一替换。区分展示名称与需要兼容保留的系统身份。新项目可采用 [项目规格示例](assets/project-spec.example.json) 记录这些决定。
4. **分别设计两类图标。** App 图标承担辨识与品牌，菜单栏图标在实际显示尺寸下优先可读。已有矢量资源优先直接修改；需要新的位图视觉时，使用环境中适用的图像生成能力。保留用户确认稿作为独立版本。
5. **验证安装与更新。** 将测试配置与日常配置隔离；更新前明确安装目标、备份与回退方式；更新后核对配置、版本、登录启动状态和实际小图显示。
6. **构建并复验交付物。** 在独立临时目录打包，解包验证签名与文件完整性，记录架构、最低系统目标、实际测试范围和真实签名/公证状态。
7. **按授权准备或执行发布。** 建立明确公开文件清单，检查私人路径、规则、日志、凭据及提交身份。写中英文介绍与发行说明。只有当前请求已经包含公开发布时，才创建仓库、推送或发布 Release；已明确授权时不重复确认。

## 关键经验

- **大图正常不等于小图正常。** ICNS 使用苹果官方工具编码并检查完整尺寸，实际检查 Finder、启动器和登录项相关界面。图标异常先区分资源错误、应用登记和缓存。
- **改名不等于改身份。** 保留或迁移 bundle identifier、配置目录、登录项引用需依据项目现状；不要机械地替换所有旧字符串。
- **测试不污染日常状态。** 如测试会改变系统级输入源等状态，配置隔离本身不够；还应控制交互范围并记录恢复方式。遇到工具不能操作的系统界面，只请用户完成必要动作，并给出短验收步骤。
- **签名完整性、公证和安全审计分别报告。** ad-hoc 签名验证通过不能写成已获苹果公证；单机测试不能写成全面兼容。
- **公开包采用文件清单。** 脚本检查通过只表示未发现其覆盖的问题，仍需人工判断内容和版权是否适合发布。
- **维护一个明确主目录。** 如有公开整理副本，记录其来源与版本；后续修改前确定主仓库，避免副本分叉。

## 可执行工具

- `scripts/make_icons.py`：1024 PNG → 完整 ICNS，使用 `sips`/`iconutil`，反向解包核对十个尺寸表示。
- `scripts/package_app.py`：只读接收已签名 `.app`，临时复制、ZIP 打包、解包复验、对比文件内容并生成 SHA-256；可选择额外验证已附带的公证票据。
- `scripts/prepare_public.py`：按显式文件清单检查与整理源码，拒绝目录、符号链接、越界路径和常见私密文件；发现内容问题时只报告位置与类别。

脚本使用 Python 3 标准库。先阅读 [脚本说明](references/script-tools.md)，再按当前任务执行；它们不会替用户安装应用、上传代码、签名、公证或接入支付。
